## 流程运行节奏 + 单步按钮卡禁用修复

用户反馈：① 单步后希望「一秒刷新一次」；② 单步运行一次后按钮就 `IsEnabled=false`（卡死）。

确认根因：`运行` 用 `DispatcherTimer` 间隔写死 600ms（`TickIntervalMs`/`_runTimer.Interval`）；`单步运行`(`StepCommand`→`StepOnce()`) 是点一次立即走一行、不走计时器；`单步运行` 按钮绑 `CanStep`，而 `CanStep` 依赖 `_currentStep`，流程走到末行后 `_currentStep==行数` → `CanStep=false` 卡死（只能先点停止）。

用户选定方案：**单步=点一次走一行（手动），连续「运行」放慢到 1 秒/行**。

### 改动（`ViewModels/FlowViewModel.cs`）
- `TickIntervalMs` 600 → `1000`（注释：单步/运行每步默认耗时，1 秒刷新）。
- `_runTimer.Interval` `TimeSpan.FromMilliseconds(600)` → `1000`（连续运行改为 1 秒/行）。
- `CanStep`：`StepPanel.Items.Count > 0 && (_currentStep < 0 || _currentStep < Count-1)` → `!IsRunning && StepPanel.Items.Count > 0`（运行期间禁用、未运行时恒可点，走完流程不再卡死）。
- `StepOnce()` 顶部加保护：当 `!IsRunning && (_currentStep < 0 || _currentStep >= items.Count)` 时重置 `_pendingNext/_ifStack/_loopStack/ClearCurrentFlags()`，并把起始行 `i` 改为「未开始或走完则从第 0 行开始、否则从 `_pendingNext`/`_currentStep` 续走」——单步走完流程后再次点击可从头重跑，暂停后续点也能接着走。

### 行为结果
单步=每点一次执行一行并按「逻辑」列跳转（保留需求 B 的跳转语义）；运行=每 1 秒自动走一行（橙色高亮 + 耗时回填每步停留 1 秒可见）；走完流程后「单步运行」不再禁用，可重头再点。

### 构建验证
`dotnet build -c Release -p:UseArtifactsOutput=true -p:ArtifactsPath=artifacts` → 0 错 0 警。需本机双击 EXE 复核节奏与按钮使能。

## Lua 编辑器：左侧每行耗时边栏 + 底部 print 输出回显

需求（两条，紧随工具栏改动之后）：① 编辑器**左侧**显示每一行执行耗时（毫秒）；② 编辑器**底部**一个 label 显示 print 输出。

### 实现思路
Lua 脚本在 MoonSharp 调试器 `GetAction(int ip, SourceRef sourceref)` 回调里逐指令触发，是挂钟计时的唯一可靠切入点。设计：仅在遇到**真实源行**（`sourceref.FromLine > 0`）时结算上一行累计耗时并开始计时当前行；同一行被多次访问（循环 / 函数内多语句）保持累计、不重复结算；**暂停期间（用户思考 / 单步）不计入**——`Resume()` 时在 `_measureStart.Restart()` 复位计时起点（Worker 线程在 `_resumeEvent.WaitOne()` 处阻塞，Resume 在 UI 线程复位，happens-before 保证不把暂停时间算进当前行）。

`Views/LuaEditorView.xaml.cs` 新增 `DispatcherTimer _lineTimeTimer`（100ms）：`StartSession` 里 `_session.Start` 后 `Start()`；Tick 中若 `_session.IsBusy` 则 `_lineTimeMargin.SetLineTimes(_session.GetLineTimesSnapshot())` 持续推给左侧边栏；`OnSessionEnded` 推最终快照后 `Stop()`；`OnLuaItemChanged` 切换流程时 `Stop()`。
逻辑上这一步是对的（把快照从 UI 推到边栏），但用户 rebuild 后仍反馈「运行不显示耗时」——说明根因不在此。

### 第二轮（真正根因：MoonSharp Run 快路径）
经 WebFetch 核对 MoonSharp 源码 `Processor_Debugger.cs`：`ListenDebugger` 在 `case ActionType.Run:` 分支是 **`return;` 直接返回**。含义：一旦 `GetAction` 返回 `Run`，引擎会跳过所有后续调试回调，整段 free run 都不再调用 `GetAction`，直到遇到断点/暂停请求/错误。
→ 第一行返回 `Run` 后，`GetAction` 永远不再被调用，计时块（位于 `GetAction` 顶部）在运行期间一次都不执行，`_lineTimes` 始终为空，边栏自然全程空白。单步之所以能显示，是因为 `StepIn`/`StepOver` 会**在每个真实源行重新回调 `GetAction`**，计时块逐行生效。

修复（`Services/LuaDebugSession.cs`，`GetAction` 的 free-run 分支）：把返回值由 `DebuggerAction.ActionType.Run` 改为 `DebuggerAction.ActionType.StepOver`：
```csharp
// 处于"继续运行"模式且不是断点 / 暂停请求 / 错误：放行。
// 注意：返回 StepOver 而非 Run —— MoonSharp 在 Run 模式下会在 ListenDebugger
// 直接 return，整段运行都不再回调 GetAction，导致每行耗时无法累计；
// 返回 StepOver 后引擎会在每一行真实源行重新回调 GetAction（从而能逐行计时），
// 但本分支在暂停逻辑之前返回，不会真正卡住 UI，脚本照常跑完。
if (!userPause && !hasError &&
    _nextAction == DebuggerAction.ActionType.Run &&
    !isBreakpoint)
{
    return new DebuggerAction { Action = DebuggerAction.ActionType.StepOver };
}
```
改为 `StepOver` 后：引擎在每行真实源行重新回调 `GetAction`（计时块逐行累计），但本分支在暂停/断点逻辑之前 return，不阻塞 UI，脚本照常跑完。断点 / 用户暂停 / 错误仍走原暂停路径，行为不变。

### 权衡（未改）
`StepOver` 不步入 Lua 函数体，故 free run 时**函数内部的行不会被计时**（单步步入 `StepIn` 才会）。若要 free run 也计入函数内部每行耗时，需把该分支改成返回 `StepIn`——会更慢（每行都回调），按用户当前诉求「尽快跑起来」保留 `StepOver`。

## 「修改」赋值逻辑走查（用户截图测试用例）

  Row 1: 就: 变量 2 修改-11

## 单步执行需按逻辑跳转（用户诉求 + 防御修复）
用户诉求：点「单步运行」后逐行执行，遇到「如果/否则/循环」等逻辑行要**判断条件并跳到规定行**（与运行模式一致）。

核查结论：当前代码 `FlowViewModel.StepOnce` **本就实现了逻辑跳转**——`单步运行` 按钮绑 `StepCommand`→`StepOnce()`（`_runTimer.Tick` 也调同一方法），`Logic` 列 ComboBox 直绑 `step.Logic`，switch case 与 `LogicOptions` 下拉项完全一致。`如果(真)→就→FindEnd 跳过否则→结束` 用 Python 复刻模拟已验证正确（执行顺序 [0,1]，Row2/Row3 不执行）。

隐藏根因（最可能导致用户看到「线性逐行不跳」）：`step.Logic` 若带不可见字符/空格（如从文件加载的旧数据、`"如果 "` 而非 `"如果"`），`switch(logic)` 全部落 `default`（`next=i+1`）→ 线性执行、不跳。下拉显示看不出空白，但 `switch("如果 ")` 匹配不到 `"如果"`。这能解释用户截图中「就 + 否则 都执行」的违和现象。

修复（`ViewModels/FlowViewModel.cs`）：全链路对 `Logic` 做 `Trim()` 防御——
- `StepOnce` 入口：`string logic = (step.Logic ?? string.Empty).Trim();`
- `MergeCompound`/`FindElse`/`FindEnd`/`FindLoopEnd` 四个跳转探测函数：`var lg = (items[k].Logic ?? string.Empty).Trim();`
- 主 switch 中判断「下一行是否 否则/否则如果」的 3 处：`(items[next].Logic ?? string.Empty).Trim() == "否则" || ... == "否则如果"`。

静态校验：FlowViewModel.cs 括号 101/101、圆括号 333/333 配平 ✅。需用户本地 VS rebuild 后复核：单步走到「如果」时按条件跳「就」或「否则」，走到「就」体尾行紧跟「否则」时自动跳走；循环开始/结束 正常重复。
