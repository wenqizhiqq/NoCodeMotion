## 3. 经验沉淀
- **GrayMatch.Wpf 渲染范式**：旋转框不要走 Cv2 烧入路线——Mat 上画旋转矩形要么
  WarpAffine（慢、占内存），要么 4 段 Line 拼（丑、像素锯齿）。WPF 矢量层 Rectangle
  + RotateTransform 是最干净的方案，缩放也走 LayoutTransform 一致处理。
- **Stretch=Uniform 下的像素→屏幕对齐**：用 TranslateTransform(ox,oy) + ScaleTransform(s,s)
  作为子元素 RenderTransform，公式与 ROI 拖拽共用同一组 scale/offset，不要各算各的。
- **异常展示可点击**：状态栏截断是常态，给用户"点开看完整"的入口比加宽更靠谱；
  弹窗里提供复制按钮方便把堆栈贴到 Bug 反馈里。

## 6. 修复：点「开启匹配」不显示匹配结果（用户反馈「点击不显示匹配情况」+「需要绿色显示 + 相似度 + 角度」）
- **现象**：点「开启匹配」按钮后运行也没崩，状态栏有结果，但右侧结果图上既看不到绿框/红框，也看不到相似度/角度的信息胶囊。
- **根因（不是匹配没跑，是显示没刷新）**：`MatchOverlay` Canvas（绑 `HasMatchResults`）和顶部信息胶囊 Border（绑 `HasMatchResult`）的 `Visibility` 依赖两个**计算属性**：
  - `public bool HasMatchResult => MatchResult != null;`
  - `public bool HasMatchResults => MatchResults != null && MatchResults.Count > 0;`

  这两个是纯 CLR getter，没有 `PropertyChanged` 通知。`RunMatchAsync` 跑完后确实把 `MatchResult = report.Match;` / `MatchResults = ...` 写到 DP 了，DP 自己的 binding 也会刷新（`{Binding MatchResult.Similarity}` 这些能看到），但**绑到计算 CLR 属性的 Visibility 不会重算**——WPF 初始化时算了一次（false → Collapsed），之后没人触发 `OnPropertyChanged(nameof(HasMatchResult))` / `OnPropertyChanged(nameof(HasMatchResults))`，所以一辈子 Collapsed。

  对比：`IsImageAcquisition` 这批同性质计算属性在 `OnSelectedStepChanged` 里调了 `RaiseTypeFlags()` 显式触发，所以参数卡能跟着 SelectedStep 切换；`HasMatchResult` 漏了同样处理。
- **修法**（`Views/VisualFlowDetailViewModel.cs`）：给 `MatchResultProperty` / `MatchResultsProperty` 加 `PropertyMetadata` 回调，DP 变化时主动 raise 计算属性：
  ```csharp
  public static readonly DependencyProperty MatchResultProperty =
      DependencyProperty.Register(nameof(MatchResult), typeof(MatchOutcome), typeof(VisualFlowDetailViewModel),
          new PropertyMetadata(null, (d, e) => ((VisualFlowDetailViewModel)d).OnPropertyChanged(nameof(HasMatchResult))));
  // MatchResultsProperty 同理，触发 HasMatchResults
  ```
- **配套确认（无需改，已正确）**：
  - 叠加层 ItemTemplate 矩形默认 Stroke=Lime，Pass=False 时切到 `#DC2626`（红），符合"绿色显示 + 未达阈值红色"。
  - ItemTemplate 内两个 TextBlock 已绑 `Score, StringFormat='相似度:{0:F3}'` 和 `Angle, StringFormat='角度:{0:F0}°'`。
  - 信息胶囊背景 `#E616A34A` 绿、Pass=False 切 `#E6DC2626` 红。
  - `UpdateMatchOverlayTransform` 已在 `ImageHost.SizeChanged` + `ResultImage`/`MatchResults` 变化时重算 `TranslateTransform(ox,oy) + ScaleTransform(s,s)`，像素→屏幕对齐公式与 `ApplyTemplateRoi` 共用，无需改。
- **验证**：`dotnet build` → **EXIT=0，CS_ERRORS=0**，XAML 编译通过无 XDG 错误。
- **教训**：WPF 里**计算 CLR 属性（`=> xxx.Yyy != null`）想被 binding 监听，必须显式 raise PropertyChanged**——DP 自身的 SetValue 不会带动计算属性。两种正规做法：
  1. 走 `PropertyMetadata(default, (d,e) => vm.OnPropertyChanged(nameof(Computed)))` 回调（推荐，DP 干净）。
  2. 改成 `ObservableObject`（CommunityToolkit.Mvvm）并用 `[NotifyPropertyChangedFor(nameof(Computed))]` 标注。
  
  凡是项目里出现 `xxx => SomeDp.?.Yyy != null` / `xxx => Collection?.Count > 0` 这种"门控 Visibility/IsEnabled"的计算属性，都要立刻追问：它在谁变化时 raise 了吗？没 raise = 永远停留在第一次评估的值。

## 7. 修复：绿框位置大小不对（用户反馈「绿框绘制位置大小不对」）
- **现象**：点「开启匹配」后叠加层绿框都画在错位 / 错尺寸的地方，与源图 chip 不严格对齐，多目标情形更明显。
- **根因（架构选择问题）**：原来 overlay 用「MatchBox 像素坐标 + 外层 Canvas RenderTransform(Translate+Scale) 映射」的方案。在以下场景均会错位：
  1. `ResultImage` DP 变化触发 PropertyChanged 时 `ResultImageView.Source` 可能尚未生效（旧源未释放），`UpdateMatchOverlayTransform` 早退并清空 `RenderTransform`，叠加上没变换 = 像素=屏幕映射丢失；
  2. `ImageHost.SizeChanged` 不在每次 MatchResults 改变时触发，Image 显示尺寸变化时无事件刷新变换；
  3. `ItemsControl` + 内嵌 `<Canvas/>` (ItemsPanel) 的 DesiredSize 路径在外层 RenderTransform 复合时容易出现 1-2px 抖动；
  4. 每帧 race（Dispatcher BeginInvoke 即使 Render 优先级也可能晚于首帧 paint）；
  5. `MatchBox.TemplateWidth/Height` 不同结果（多尺度 / 视差）下不一致时，叠加层若仍以单尺度换算会出现"框大小差异"。
  本质上：**「RenderTransform 拿来在 Image 上对齐像素」组合太脆弱**——任何时序抖动都会被叠加上，结果"看起来绿框大小位置都对不上"。
- **修法（彻底重构）：屏幕坐标预投影，把 RenderTransform 拿掉**
  - `Models/MatchBox.cs`：新增 `OverlayBox`（`ScreenLeft/Top/Width/Height/Angle/Score/Pass`），静态 `OverlayBox.Project(matchBox, scale, offsetX, offsetY)` 一次性投影好。
  - `Views/VisualFlowDetailViewModel.cs`：新增 `OverlayBoxes` DP（`ObservableCollection<OverlayBox>`）和 `HasOverlayBoxes` 计算属性。
  - `Views/VisualFlowPage.xaml.cs`：新增 `ProjectOverlayBoxes()`；订阅 `ResultImage` 变化 / `MatchResults` 变化（含 `CollectionChanged`）/ `ImageHost.SizeChanged`，每次按当前 `src.PixelWidth/Height` + `ImageHost.ActualWidth/Height` 公式 `scale = min(hostW/srcW, hostH/srcH); offset = (host - src*scale)/2` 重算并写回 `_vm.OverlayBoxes`。
  - `Views/VisualFlowPage.xaml`：叠加层 ItemsControl 从 `{Binding MatchResults}` 改为 `{Binding OverlayBoxes}`，ItemTemplate 从 `{Binding LeftTopX/Y/Width/Height/Angle}` 改为 `{Binding ScreenLeft/Top/Width/Height/Angle}`，外层 `MatchOverlay` 的 `RenderTransform` 删掉，Visibility 绑 `HasOverlayBoxes`。Angle 已是 WPF 顺时针方向（OpenCV 逆时针负值），不再需要 `AngleNegateConverter`。
- **优点**：
  1. 像素→屏幕映射完全确定：每个 OverlayBox 都是 `(LeftTopX*s + offset, ...)`，所有结果用同一 scale/offset，框之间相对位置与源图严格一致。
  2. 与 ResultImageView 的 Stretch=Uniform 完全脱钩——Image 怎么渲染是 Image 的事，Overlay 用屏幕坐标，永远不需要等布局/Dispatcher。
  3. `Angle` 已统一在投影时取反，模板 `DataTemplate` 不再需要 converter。
  4. ImageHost 尺寸变化或 ResultImage 切换都会重新投影，框永远跟随显示区域。
- **验证**：`dotnet build` → **EXIT=0, CS_ERRORS=0**。重构后 XAML 结构不变，仅 ItemsControl 数据源与字段名切换；VisualFlowPage.xaml 仍 0 XDG 错误。
- **教训（架构经验）**：
  1. 在 WPF 里「Image.Source + 外层叠加层 RenderTransform 做坐标映射」的方案对**布局时机非常敏感**（ResultImage Source 切换、Image.SizeChanged、ItemsControl 重排、Dispatcher 优先级都要追平），遇到 "框错位" 类问题极难调；改成「预投影到屏幕坐标 + 直接 Canvas.Left/Top」一劳永逸。
  2. 同类已落地参考：GrayMatch.Wpf 用 `Stretch="None"` + Grid.LayoutTransform 整体缩放避免此问题；本项目受限于 `Stretch="Uniform"` 给的「等比缩放+居中」，对应做法就是预投影。
  3. 任何 overlay / 覆盖层涉及"按显示区域换算坐标"的场景，**优先预投影 + 单向绑定**，不要依赖 RenderTransform 链。

## 10. 真因：点「开启匹配」绿框不显示 = OverlayBoxes 缺少 PropertyMetadata 回调
- **现象（用户文字反馈，非截图）**：点「开启匹配」按钮（XAML 命令 `RunMatchCommand`，按钮文案"开启匹配"，用户称"开始匹配"），状态栏/信息胶囊都显示匹配完成、找到 N 个目标，但右侧结果图上**完全没有绿/红框**。
- **真因**：§7 重构后，叠加层 `MatchOverlay` 的 `Visibility` 绑 `HasOverlayBoxes`（计算 CLR 属性 `=> OverlayBoxes != null && OverlayBoxes.Count > 0`）。而 `OverlayBoxesProperty` 的注册**没有 `PropertyMetadata` 回调**去 raise `HasOverlayBoxes`。于是 `ProjectOverlayBoxes()` 写回 `_vm.OverlayBoxes` 时，绑定 `HasOverlayBoxes` 永远停在首次的 `false` → `MatchOverlay` 一辈子 `Collapsed`，数据有了但画布不显示。这是 §6 同一个坑（计算属性门控 Visibility 必须显式 raise）在叠加层自身的重演。
- **修法**（`Views/VisualFlowDetailViewModel.cs`）：
  ```csharp
  public static readonly DependencyProperty OverlayBoxesProperty =
      DependencyProperty.Register(nameof(OverlayBoxes), typeof(ObservableCollection<OverlayBox>),
          typeof(VisualFlowDetailViewModel),
          new PropertyMetadata(null, (d, e) =>
              ((VisualFlowDetailViewModel)d).OnPropertyChanged(nameof(HasOverlayBoxes))));
  ```
- **配套加固**（`Views/VisualFlowPage.xaml.cs` `ProjectOverlayBoxes`）：原来读 `ResultImageView.Source as BitmapSource`（控件侧，依赖绑定传播时机，可能在 `MatchResults` 变化时还没刷新 → 拿不到像素尺寸）。改为直接读 **VM 同步 DP** `_vm.ResultImage as BitmapSource`，与 `_vm.MatchResults` 同源同步，避免"MatchResults 已就绪但 Image 控件 Source 滞后"竞态。再加 `_projRetry` 计数（≤30 次 `DispatcherPriority.Render` 延迟重试）兜底 `ImageHost.ActualWidth=0` 的首次布局 race。
- **验证**：`dotnet build`（PowerShell 绝对 `dotnet.exe`）→ **EXIT=0，CS=0**；24 条 warning 全为 `FlowRunnerService`/`OperatorViewModel`/`VisionEngine` 既有项，与本次改动无关。沙箱 EDR 会 kill 进程，无法本机运行，需用户在 VS `Ctrl+Alt+F7` Rebuild 后点「开启匹配」目测。
- **教训（高频坑）**：WPF 里**凡是 `Visibility`/`IsEnabled` 绑到 `=> SomeDp?.Count > 0` / `!= null` 这种计算 CLR 属性**，该 DP 注册务必带 `PropertyMetadata(default, (d,e)=>vm.OnPropertyChanged(nameof(Computed)))`。本项目已踩两次（§6 `HasMatchResults`、§10 `HasOverlayBoxes`）——凡新增"门控型计算属性"，先问自己：它在谁变化时 raise 了？没 raise = 永远初始值。

## 11. 主流程不循环运行 = RunOneFlow 缺外层 while，按 FlowRole 分支修复
- **现象（用户截图+文字）**：操作员点「启动」后，操作台右侧流程列表 10 条里**只有 脚本流程（Lua）**显示绿色「运行」徽章，其余 6 条主流程（自动取料、装配循环、工位1出料、工位2包装、全流程、视觉检测）停留在「就绪」，3 条复位流程停在「复位」。用户文字：「操作员运行了，所有主流程都需要循环运行」。
- **根因**：之前 `RunOneFlow`（`ViewModels/FlowRunnerService.cs`）对非 Lua 流程只 `exec.Run(ct)` 一次就跑完了，循环只在「循环开始/循环结束」块内部按 SetValue 次数循环；跑完整条 Steps 列表就 status→Idle 退出。所以 Lua 流程一直「运行」（`RunOneFlowLua` 本身有 `while (!StopRequested && !EStopRequested)` 外层循环），主流程跑完一轮就没了。
- **修法**：在 `RunOneFlow` 里按 `FlowItem.Role` 分支——主流程（`Role=Main`）跑外层 `while` 每轮重新 `new FlowExecutor` 跑全部 Steps；复位流程（`Role=Reset`）保留单次执行（归位复位不能循环）。每轮 `exec.ClearCurrent()` 清掉上一轮高亮行；异常时 `Thread.Sleep(500)` 防紧密重试刷屏。顺手把 `flow.Kind.ToString() == "Lua"` 这个脆弱字符串比较换成 `flow.Kind == FlowKind.Lua`。
- **验证**：`dotnet build`（PowerShell 绝对 `dotnet.exe`）→ **EXIT=0，CS=0**；26 条 warning 全为既有 nullability 警告，与本次无关。沙箱 EDR 杀进程，需用户 VS `Ctrl+Alt+F7` Rebuild 后在操作台点「启动」目测：主流程徽章应在「运行」保持，按「停止 / 急停」后切回「停止」。
- **教训**：流程执行器要按「运行模式」分支（Main 循环 / Reset 单次 / Lua 走编辑器），不要一刀切。`enum.ToString() == "字符串"`" 是定时炸弹——一旦枚举改名就静默漏分支（Lua 退化为普通 Table 流程执行器）。
