## 工程师页 ComboBox 显示类名 + 全员水印

### 1. 工程师页 ComboBox 显示类名（"NoCodeMotion.Models.PointTat" 截图）
- **根因**：`Views/EngineerPage.xaml` 第 280-281 行 ComboBox 用 `DisplayMemberPath="Name"` + `Style="{StaticResource CellComboStyle}"`（`CellComboStyle` 强制 `IsReadOnly=True`）。
  当 `EditorItemBase.Name` 在某些路径（WPF 反射解析 / ItemContainerStyle 模板 / `IsReadOnly` 嵌入 TextBox）下被 binding 解析成 `null` 时，WPF 会回退调用 `object.ToString()`，于是显示 `NoCodeMotion.Models.PointTable` 全类型名。
- **修法（两道闸口）**：
  1. `Models/EditorItemBase.cs` —— 重写 `ToString()`：`null/空白 → "未命名"`，否则返回 `Name`。任何 binding 失败路径下都不再泄露类型名（也救回日志 / 调试窗口）。
  2. `Views/EngineerPage.xaml` 选择工位 ComboBox —— 改用 `ItemTemplate = DataTemplate { TextBlock Text={Binding Name, FallbackValue=未命名工位} }`。直接 ItemTemplate 路径不依赖 DisplayMemberPath，绑不到 Name 时用 FallbackValue 兜底。
- 验证：`dotnet build` → **0 error / 24 warning（历史 baseline）**。

### 3. 一个被加固的 WPF 经验
- ComboBox 用 `DisplayMemberPath` 在多种样式（`CellComboStyle` `AppleCombo` `AppleComboReadOnly`）下都可能因回退路径显示类型名。**最小成本的兜底是给数据模型 `override ToString()` 返回 Name**，所有 binding 失败路径立刻恢复为可读文字，对 UI / 日志 / 调试都有用。

### 4. 视觉流程模板匹配改用 GrayMatch.Wpf 的 OpenCV 旋转不变 NCC 核心
- **需求**：用户要求 NoCodeMotion 视觉流程页「模板匹配」改用 `D:\wqz\code\GrayMatch\GrayMatch.Wpf` 那套 OpenCV 旋转不变匹配（之前是 VisionEngine 自写 matchTemplate + WarpAffine 角度循环，精度/鲁棒性不足）。
- **接入方式**（关键）：GrayMatch.csproj 是 WinExe，**不能**作 ProjectReference；改用**源码级共享**——`NoCodeMotion.csproj` 直接 `<Compile Include="..\GrayMatch\GrayMatch\RotatedTemplateMatcher.cs" Link="Vision\GrayMatch\..." />`（连同 `MatchResult.cs` / `DefectResult.cs`），与 GrayMatch 工程共用同一份源（单一事实来源）。
- **native 依赖**：`<None Include="..\GrayMatch\GrayModelNative\build-ninja9\GrayModelNative.dll" CopyToOutputDirectory>` + AfterBuild Target 从 VS2022 redist 拷 `vcomp140.dll`（OpenMP 运行时，native matcher 必需）。NoCodeMotion 已自带 `opencv_world480.dll` / `OpenCvSharpExtern.dll`（同源 OpenCvSharp 4.13）。
- **算法替换**：`Services/Vision/VisionEngine.cs` 的 `RunMatch` 删掉自写 `matchTemplate`+角度`WarpAffine` 循环，改 `new GrayMatch.RotatedTemplateMatcher()` → `SetSource(灰度cur)`/`SetTemplate(灰度tpl)` → `matcher.Match(pyramidLevels:0, angleStart:0, angleEnd:AngleRange, angleStep:1°, nccThreshold:ScoreThreshold, maxOverlap:0.3, topN:1)`；`UseContour=(MatchMode=="轮廓匹配")`；取 `results[0]` 填 `report.Match` 并画绿/红框。
- **为什么 pyramidLevels:0**：GrayMatch 金字塔分支（≥1）深层（1/8 下采样）会因 `coarseThr=0.15` 把旋转/小目标 NCC 压到阈值以下漏检（GrayMatch.Tests 已验证 `pyramid=4` 只 1/4）；0 = 传统两遍（0.25×粗+0.35×精），稳健。
- **验证**：`dotnet build` → **0 error / 24 warning（无新增）**；`bin/Debug/net10.0-windows/` 下 `GrayModelNative.dll`(97KB)+`vcomp140.dll`(193KB)+`opencv_world480.dll` 均就位。P/Invoke 链路与 GrayMatch.Wpf 完全一致（同源代码+同 OpenCvSharp 4.13+同 native DLL），运行时可直接拉起验证（沙箱 EDR 仍会拦 EXE，无法在此实跑截图）。

### 5. 匹配「这么慢」+ 后台任务未观察异常
- **用户截图症状**：4×3=12 个同朝向十字叉目标，只框出 1 个；状态栏红字 "A Task's exception(s) were not observed either by..."。
- **慢的根因**：
  1. `topN:1` 只显示 1 个匹配，但 GrayMatch 搜索时间与 topN 几乎无关（搜全图后 NMS 保留前 N），所以"想要多个匹配"靠改 topN；
  2. **真正的慢因是 `angleStep:1°` × `AngleRange:355°`**——native 在 [0,355°] 每 1° 一步 = 356 步 × 全分辨率 NCC × 12 目标。截图里目标同朝向，根本不需要这么细的扫描。
- **后台异常根因**：`Views/VisualFlowDetailViewModel.cs` 的 `RunMatchAsync` 第 295 行 `await Task.Run(...)` **没有 try/finally**——一旦 `VisionEngine.Run` 抛错，`IsRunning`永远 true / `CanRun`永远 false /按钮永久变灰；同时异常从 `async Task` 经 `_ = RunMatchAsync()` fire-and-forget 抛出 → `UnobservedTaskException` → 状态栏红字（。
- **修法**：
  1. `VisionEngine.RunMatch`：`angleStep` 智能选——`≤0°`→`0`、`≤30°`→`1°`（短旋转精扫）、`>30°`→`5°`（长范围粗扫提速 5 倍，GrayMatch 的 0.35× 精修步 3° 兜底）。`topN:1`→`12`（图里十二个全框出，搜索时间几乎不变）。
  2. `RunMatchAsync`：包 try/catch/finally——catch 写 `RunStatus` + `StatusBarService.ReportException`，finally 强制 `IsRunning=false`/`CanRun=true`。异常不再逃逸到 `UnobservedTaskException`。
- **验证**：`dotnet build` → **0 error / 24 warning（baseline，无新增）**。同朝向场景预计提速 5 倍；12 个目标全框出；异常路径不再卡死按钮。
