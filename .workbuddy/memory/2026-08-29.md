## 用户问"为什么图像采集，没有文件打开按钮"——实为 2 个 bug 叠在一起

### Bug ① 真正的"没按钮"：XAML 漏写了浏览控件
- 上一轮加图像采集卡（文件路径/文件夹/相机）时只放了 TextBox 手动输入路径，**没配套"浏览"按钮**——纯遗漏。模板路径、预处理第二张图也同类缺失。
- 修法：VM（`Views/VisualFlowDetailViewModel.cs`）加通用 `BrowsePathCommand`，参数为属性名（SavePath/FolderPath/TemplatePath/PreImage2Path）：
  - `FolderPath` → `Microsoft.Win32.OpenFolderDialog`（.NET 8+ 新增，net10.0-windows + UseWPF 即可用）
  - 其余 → `Microsoft.Win32.OpenFileDialog`，过滤器 `*.png;*.jpg;*.jpeg;*.bmp;*.tif;*.tiff`
  - 用 `try/catch` 包住 `ShowDialog`，失败时把异常消息写回 `RunStatus`——**应对 memory 里记录的"奇安信 EDR 静默阻断 OpenFileDialog"**，避免用户点了没反应还以为没按钮
- XAML（`Views/VisualFlowPage.xaml`）四处路径行加 `<Button Content="浏览" ... Command="{Binding BrowsePathCommand}" CommandParameter="..."/>`（文件/文件夹/模板路径/第二张图），按钮停靠右侧，TextBox 改为 LastChildFill 填中间。
- 构建：dotnet build 0 错误 ✓（OpenFolderDialog 编译通过确认 .NET 10 可用）。

### Bug ②（更隐蔽）：视觉流程页 SelectedStep 永为 null → 所有参数卡全 Collapsed
- 现象：加了按钮后 PrintWindow 截图，发现右侧**只显示"通用参数"卡，采集/匹配/缺陷/测量/通讯 5 张卡全没显示**——ListBox 里步骤2"图像采集"也没蓝色高亮。
- 根因：`Views/VisualFlowPage.xaml.cs` 的 `ApplySelection()` 只同步了 `_vm.Steps` / `_vm.Name`，**从未初始化 `_vm.SelectedStep`**。VM 的 `SelectedStep` 是 DP，默认 null → ListBox `SelectedItem` 双向绑也是 null → 没有选中项 → VM 的 `IsImageAcquisition = SelectedStep?.StepType == "图像采集"` 永远是 false → 采集卡 Visibility=Collapsed → 按钮即使加了也看不见。
- 修法：ApplySelection 末尾加 3 行——Steps 非空且 SelectedStep 为 null 时自动选 `Steps[0]`，让用户一进入视觉流程就看到第一个步骤的参数。`AddStepCommand` 已有 `SelectedStep = step`，删除时 `SelectedStep = null`，无需额外处理。
- 验证：PrintWindow 截图（1721×1033，最大化窗口）——左侧 ListBox 步骤2 蓝色高亮 ✓、通用参数可见 ✓、**图像采集参数卡可见** ✓、**文件路径行 + 蓝色"浏览"按钮**可见 ✓。

### 截图技术（沙箱里 PrintWindow 抓 WPF 窗口）
- `SetForegroundWindow` 在本环境被 Windows 前台锁定限制（VS 抢前台不让别的进程切过来），`ImageGrab.grab(all_screens=True)` 只能抓前台。
- 解决：Python ctypes 调 `user32.PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT=0x02)` 渲染任意窗口到位图，再用 `gdi32.GetDIBits` 读像素，PIL 保存 PNG。**完全不依赖窗口是否前台**。
- 配合 `user32.ShowWindow(hwnd, SW_MAXIMIZE=3)` + `sleep(1.2)` 可让 ScrollViewer 区增高，参数卡可见。

### 踩坑（耗时 3 次构建才解决）："Grid * 列 + 多列 Auto 会把 TextBox/Unit 推出视口"
- 第一次截图：滑块位置正确，但 TextBox 数字和单位"ms/px"完全不可见。怀疑 AppleTextField 的 `MinWidth=120` 把 TextBox 撑成 120px。
- 第二次：加 `Style NumSliderBox BasedOn AppleTextField` 覆盖 MinWidth=0 + HorizontalAlignment=Stretch。仍然不可见。
- 第三次（**真因**）：数学算账——右侧面板宽 ~1061px，列分配 Label(92) + Slider(*) + TextBox(56) + Unit(20) = 168 + Slider。Slider `*` 占满 1061-168=893px，**TextBox 起点在 x=1685（窗口坐标），已超过窗口 1721 宽度的视口边界**。TextBox 和 Unit 渲染了但在屏幕外。
- 最终修法：`ColumnDefinition Width="*" MaxWidth="320"`——给 Slider 封顶，让 TextBox+Unit 留在视口内。FontSize=13 增加 TextBox 可读性。
- 经验（WPF 通用）：**`Grid` 用 `*` 列时务必加 `MaxWidth`，否则 `*` 会无界扩张把后面的列推出视口**。DockPanel 的 `LastChildFill` 类似。复杂行布局最好用 Grid + 显式 MaxWidth/MinWidth 约束。

### 经验沉淀
- Slider+TextBox 联动最简方案：两者都绑同一个 DP（`FrameworkPropertyMetadataOptions.BindsTwoWayByDefault`），XAML 里省写 Mode=TwoWay。`UpdateSourceTrigger=PropertyChanged + Delay=300` 避免输入中间态（"0."、"-"）触发转换失败。
- 通用行控件（Label + 控件 + 单位）适合封装成 UserControl，**避免 11 处重复 XAML**，也方便以后统一调样式。
- 工程 JSON 保存状态导致"用户上次操作的值"会持久化，重启应用后还在；调试时若看到非默认值，先检查是不是用户实际改过（而非 bug）。

### 经验沉淀（WPF 布局 + 沙箱截图）
- **`Grid *` 列 + ScrollViewer 是经典坑**：ScrollViewer 内容 MinWidth > 分配宽度时，`*` 列会被撑大挤压相邻固定列（甚至覆盖 Border）。ScrollViewer 自身的 `HorizontalScrollBarVisibility=Disabled` 只能阻止横滚条显示，**不能让 ScrollViewer 强制收缩到父容器宽度**。
- **左右布局优先用 `DockPanel` 而非 `Grid *`**：DockPanel 按声明顺序精确分配，元素不会溢出。Border Dock=Right Width=N 固定占右，ScrollViewer 无 Dock 走 LastChildFill 自动填满剩余。
- **沙箱 PrintWindow 抓 WPF 窗口的陷阱**：`user32.PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT=0x02)` + `gdi32.GetDIBits` 通常能抓 WPF 内容，但**当窗口被频繁 Stop+Start 时，WPF DirectComposition 缓存可能未及时刷新**，抓的图仍是旧帧。**用 RedrawWindow + SetWindowPos 强制重绘仍可能无效**。**最可靠是用户提供截图**作为真相源（实机渲染和 PrintWindow 抓的图可能不一致）。
- 改 XAML 时**容易在 Edit 替换中漏删/多删元素**（如残留的旧 Border + 多个孤儿 `</Grid>` + 缺 `</DockPanel>`），导致结构错乱但 build 仍 0 错误（结构错乱只在运行时才暴露）。**改完务必 Read 全文确认开合标签数对得上**。

### 真因：字段默认值是示例，LuaEditorView 不监听 INPC（用户："出现了这个，切换之后才空lua了"）
- 上一轮把 `LuaTemplates.Get("空项目") => ""` 改对了，但用户实际还是看到示例——切到别的流程再切回来才空。
- **真因链路**：
  1. `FlowItem._luaSource = DefaultLuaTemplate;`（**字段默认值是 40 行示例**）
  2. `Add()` 创建新 FlowItem → LuaEditorView 的 DataContext 切到新项 → **首次读 `DataContext.LuaSource` = DefaultLuaTemplate 全文**（40 行示例显示在编辑器）
  3. `OpenCreateDialog` 接着执行 `SelectedItem.LuaSource = ""` → 触发 INPC → 但 **LuaEditorView 看起来没监听 INPC**（典型 OneTime 绑定或 DataTrigger 缓存），编辑器仍显示示例
  4. 切到别的流程（LuaSource = 示例）→ 切回（LuaEditorView 重新读 DataContext.LuaSource = `""`）→ 显示空 ✓
- **根本修法**：改 `FlowItem._luaSource` 字段默认值为 `string.Empty`（不是 `DefaultLuaTemplate`）——这样**新流程首次读就是空**，不依赖 INPC 触发
  - `DefaultLuaTemplate` 常量**保留**（在 LuaStudio 编辑器里仍可作"重置示例"按钮用）
  - `LuaTemplates.Get("空项目") => ""` 仍保留（覆盖任何来源的旧值）
  - `OpenCreateDialog` 仍显式赋 LuaSource（确保非"空项目"模板的赋值能触发 INPC）
- 旧流程（之前用 `DefaultLuaTemplate` 默认值建的）仍有问题（JSON 反序列化保留示例值）——用户需要手动删除重建或点"重置"按钮清空
- 构建：dotnet build 0 错误 ✓
- 经验：**"字段默认值"对 UI 控件影响极大**——编辑器/列表的**首次读取**发生在 INPC 触发之前，字段默认值就是用户第一眼看到的内容。给"空"模板/新对象，字段默认值**必须是真正的空**（`string.Empty`），不能是"示例/占位符"。修法优先级：① 改字段默认 → ② 改工厂方法 → ③ 改赋值顺序（最弱）。

### 修：改字段默认后"其他默认项目也空了" → 改 LuaEditorView 订阅 INPC 自动刷新（用户："其他默认项目也是空lua了，你还是自动刷新一次吧"）
- **副作用**：上一步把 `_luaSource` 字段默认改为 `string.Empty` 后，**所有模板都空了**（不只空项目）。因为 `LuaEditorView` 的 `LuaItem` 是 **DependencyProperty**，只有 **LuaItem 引用变化**时才在 `OnLuaItemChanged()` 里读一次 `LuaItem.LuaSource`；**它根本没订阅 FlowItem 的 INPC** → 程序改 `LuaSource` 后编辑器永不刷新，显示的一直是字段默认值（现在是空）。
- **修法（改 `Views/LuaEditorView.xaml.cs`）**：
  - 加字段 `private FlowItem _subscribedItem;`
  - `OnLuaItemChanged()` 开头**退订旧项 + 订阅新项** `item.PropertyChanged += OnLuaItemPropertyChanged;`
  - 新增回调 `OnLuaItemPropertyChanged(sender, PropertyChangedEventArgs e)`：
    - 只处理 `e.PropertyName == nameof(FlowItem.LuaSource)`
    - 非 UI 线程用 `Dispatcher.BeginInvoke` 封送回来
    - **关键防抖**：`if (src == Editor.Text) return;` ——用户在编辑器打字也会回写 LuaSource 触发 INPC，若不比对会造成光标跳动/内容覆盖；只有**外部**改的（与编辑器内容不一致）才重载
    - 重载时包 `_settingText = true/false`（避免把程序设的文本又回写 LuaSource 造成循环）
    - 重载后调 `CheckSyntaxNow()` 刷新语法检查
- **无循环验证**：① 用户打字 → Editor.Text 变 → 回写 LuaSource → INPC → 回调比对 `src == Editor.Text` → 不重载 ✓；② 外部设 LuaSource=示例 → INPC → 回调比对不等 → 重载（期间 `_settingText=true` 阻止回写）→ 无循环 ✓
- 构建：dotnet build 0 错误 ✓
- 经验：**"自定义控件只在其 DP 引用变化时重载内容"是常见设计**，外部改子属性不会刷新。让控件订阅数据项的 INPC 即可自动刷新，但**必须做"内容比对"防抖**，否则用户编辑会被自己的回写打断。

### 删后自动选下一个 + 工具栏新增"清空"按钮（用户："删除按钮，删除之后默认选择写一个流程，方便删除，还需要一个删除全部流程的按钮，需要弹窗确定"）
- **基类 `ListEditorViewModel<T>.Delete()` 问题**（L73-78）：`Items.Remove(SelectedItem)` 后**直接 `SelectedItem = null`**——删完不自动选下一个，连续删除体验差（每次得手动点下一个）。
- **重写 `FlowViewModel.Delete()`**：删前记 idx → `Items.Remove`（触发基类 OnItemsChanged 取消订阅+保存）→ 按"原 index 的下一个/越界则上一个/空集合置 null"自动选。**比基类多一行 `SelectedItem = Items[idx]`**（或 `Items[Count-1]`）就解决。
- **新增 `DeleteAllCommand`**（弹窗二次确认防误删）：`new Views.ConfirmDialog("删除全部流程", "确定删除全部 N 个流程？此操作不可撤销。", "全部删除")` → 确认后**快照 `Items.ToList()` 逐个 Remove**（不用 `Items.Clear()`，因为基类 `OnItemsChanged` 对 Clear 不触发 OldItems，回调不到 UnsubscribeItem，会内存泄漏）。
- **`FlowPage.xaml` LeftToolbarContent 末尾加"清空"按钮**（在"添加视觉"之后），Command 绑 `DeleteAllCommand`，用 `DeleteIcon` 图标 + 8px 左边距与其他按钮分隔。不污染 `EditorPage` 默认工具栏（Point/Camera 等页不受影响）。
- 构建：dotnet build 0 错误 ✓
- 经验：**批量删除用 `ToList()` 快照 + 逐 Remove**（保留每项的 OnItemsChanged 通知 + 取消订阅），**不要用 `Items.Clear()`**（基类 CollectionChanged 事件 Reset 不带 OldItems，UnsubscribeItem 不会被调用 → 内存泄漏 + 残留订阅）。
