## 09:1x 字符识别结果叠加：每行文字画绿框 + 框上方绿字标签

用户提问：**「为什么字符识别没有显示图像的匹配情况」**。确认口径（AskUserQuestion）：① 显示粒度 = **每行文字画绿框+绿字**；② 文字标签 = **要，框上方标识别文字**。

### 根因（不是坏了，是从来没实现）
图上的「匹配情况」叠加层数据源是**单线**的：
`VisionReport.Matches → VM.MatchResults → ProjectOverlayBoxes() → XAML MatchOverlay`。
`report.Matches` **全工程只有模板匹配 `RunMatch` 一处写入**（`VisionEngine.cs:474-477`）。
`RunOcr` 原来只做两件事：① 在注释画布上画**一个** ROI 矩形（且**只有框选了 ROI 才画**）② 往 `report.Results` 加一条文字结果（右侧列表）。它**从未枚举 `ocr.Lines[i].Words[j].BoundingRect`** → 根本没有「哪行文字在哪」的坐标，自然画不出框。

### 实现（四环 + 两处配套）
1. **模型** `Models/MatchBox.cs`：新增 `TextBoxItem`（源图像素坐标：Left/Top/W/H/Text/Pass）与 `TextOverlayBox`（屏幕坐标 + `Project(tb, scale, offsetX, offsetY)`）。
2. **引擎** `Services/Vision/VisionEngine.cs`：`VisionReport` 新增 `List<TextBoxItem> TextBoxes`；`RunOcr` 逐行 `line.Words` 取 `word.BoundingRect` 并集，**加回 ROI 原点** `Left = bx + rx, Top = by + ry`，写入 `TextBoxes`。**故意不并入 `report.Matches`**（会被「共找到 N 个目标」/`MatchResult` 消费而污染匹配统计）。
3. **VM** `Views/VisualFlowDetailViewModel.cs`：新增 `OcrTextBoxes` / `TextOverlayBoxes` 两个 DP + `Has*`；三处运行入口回填（两种缩进各一处/两处）；切步骤清空。
4. **页面** `Views/VisualFlowPage.xaml(.cs)`：`ProjectOverlayBoxes()` 改成 `anyMatch || anyText` 都投影，**两类框共用同一 scale/offset**；新增 `HookOcrTextCollection`；XAML 在 `MatchOverlay` 之后加第二个 `Canvas x:Name="TextOverlay"`（绿 `Lime` 框 + 框上沿外侧 `Canvas.Top="-20"` 绿字标签，Pass=False → `#DC2626` 框 / `#FF6B6B` 字）。

**为什么走向量叠加层而不是 OpenCV `PutText`**：`PutText` 只有 Hershey 字体、**中文会渲染成 `???`**；WPF TextBlock 能正常显示中文，且随 `ImageHost` 的缩放/平移一起走。

### ★ 顺带挖出的真 bug：DP 变化不会自动抛 INPC
`VisualFlowDetailViewModel` 是 `DependencyObject` + 自己的 `PropertyChanged` 事件，但**只注册了 DP 回调抛 `HasXxx`**，从没抛过 `ResultImage` / `MatchResults` / `OcrTextBoxes`。于是 `VisualFlowPage.OnVmPropertyChanged` 里那三个分支是**死代码** → 叠加层只能等 `ImageHost.SizeChanged`（缩放窗口 / 切页）才刷新，**跑完一次不刷新绿框**。
修：VM override `protected override void OnPropertyChanged(DependencyPropertyChangedEventArgs e)` → `base` + 把 `e.Property.Name` 也 `PropertyChanged?.Invoke`。冒烟段 Q 里加的「匹配框也走同一投影路径」断言就是钉这个 —— 修之前它必挂。

- `VisionEngine.cs` 的 `Replace('\r', ' ')` 变成字面量里含真换行 → C# 编译错（已改成直接 `.Trim()`，`OcrLine.Text` 本来不含换行）；
- `guard_sources.py` 的 `.replace("\r\n", "\n")` 被拆成 3 行 → Python 语法错。
**对策**：需要往文件里写反斜杠时，用 `chr(92)` 拼，或干脆避免；写完必须 `repr()` 复核。

### ★ 关键设计决定
1. **数学约定**：`X=A1·u+A2·v+A3`、`Y=B1·u+B2·v+B3`；像素当量 `√(A1²+B1²)`；`AngleX=atan2(B1,A1)`。**轴向对齐时 Y 方向角 = 90° 而不是 0°**（第一次写断言就差点按直觉写成 0，模拟后才纠正）。
2. **求解器/检测器不依赖 OpenCV**：`dotnet exec` 下 `opencv_world480.dll` 不在搜索路径，标定又最需要「可离线断言」→ 纯托管实现，冒烟因此能端到端跑真流程。
3. **执行器零硬件依赖**：`Func<string,double> ReadAxisPosition` / `Action<string,double> MoveAxisAbs` / `Func<string,bool> IsAxisDone` / `Func<(byte[]?,int,int)> GrabFrame` / `Action Guard`。既避开 `Services.Vision → Services` 环依赖，也让冒烟用**合成圆斑 + 假轴**验证「还原出的像素当量/方向角/旋转中心」。
4. **三条安全硬约束**：仿真桩 `StubHardwareBridge` 直接中止；轴名按名解析失败即失败（**绝不拿轴 0 顶上**）；`GrabFrame` 取不到图返回空帧让执行器报错（**不回退合成图** —— 合成图会悄悄产出垃圾参数）。
5. **停止必须冒泡**：`CalibrationRunner` 3 处 + `VisionEngine.Run` 2 处 `catch (OperationCanceledException) { throw; }`。吞掉的话按「停止」后轴会继续走完 14 个点。

### ★ 本轮踩的坑
1. **CRLF 行尾断言写反**：`save()` 里拿**原始** `\r\n` 计数与写盘后的比 → CRLF 文件必然「drift」（写盘时每个 `\n` 都转成 `\r\n`）→ 假报错、只写了 1/3 的文件。修：先 `crlf = b.count(b'\r\n') > 0`，再断言 `b.count(b'\r\n') == (b.count(b'\n') if crlf else 0)`。
2. **补丁锚点必须 `repr()` 核对**：两处断言 `count 0` —— ① 我按记忆写了 `MatchOutcome` 的注释「相似度（= Score…）」，实际是「相似度 0~1。」；② 非 raw 字符串里的 `\"` 会被折叠成裸 `"`，导致搜索文本少一个反斜杠（AI 交换的 `\"标定方式\":`）。修：`chr(92)`/`chr(34)` 拼转义引号 + 写盘前 `assert NEW.count(chr(92))==0`。
3. **守卫里 `find` 要找唯一锚点**：`_xs.find("流程（")` 命中了文件里更早的另一处同名文字 → `int()` 解析炸。改成 `Add("流程（` 前缀。
