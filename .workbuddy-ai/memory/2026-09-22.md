## 19) 移植 DMC-E 3000/5000 官方例程：让轴 / IO 在总线卡上真能跑

需求原话：「`D:\wqz\运控\DMC-E例程----3000、5000系列\总线卡---20260909\C#` 这里面的例子，
你移植到项目里面，需要轴IO可以跑起来」。

### 根因：项目里原来的雷赛层是**只按脉冲卡写的**，在总线卡（EtherCAT）上必然不动

LTDMC.dll 里有**两套互不相通的函数族**，这是「函数返回 0 但轴不动」的总根源：

- `dmc_*` = **板卡本地资源** → 脉冲卡（DMC2410 / DMC1000）。轴 = 卡上第几路；IO = 卡上第几位；
  伺服使能 = 一个物理引脚（`dmc_write_sevon_pin`）。
- `nmc_*` = **总线主站资源** → EtherCAT / CANopen 卡（DMC-E 3000 / 5000）。
  IO 按「从站节点号 + 站内位号」寻址；伺服使能**必须**走 `nmc_set_axis_enable`（CiA402 状态机，
  总线伺服没有本地使能脚）。

原实现只声明了 `dmc_*`，整个 `nmc_*` 族**一个都没声明** → 总线卡上所有轴 / IO 调用静默走错分支。

### 从官方例程核出来的事实（不是猜的）

- **总线卡上「运动」仍然用 `dmc_*`**（例 1 定长运动 / 例 7 回原点实测）：
  `dmc_set_profile_unit(card, axis, startVel, maxVel, tacc, tdec, stopVel)`（**7 个参数**）→
  `dmc_pmove_unit(card, axis, dist, posiMode)`；位置读 `dmc_get_position_unit(card, axis, ref pos)`；
  `dmc_check_done`（**0 = 运动中，1 = 到位**）；`dmc_set_position_unit`；`dmc_change_speed_unit`；
  `dmc_reset_target_position_unit`；`dmc_stop`。**轴号就是一个整数索引，不用换算成从站地址。**
- **只有三件事分族**：伺服使能（`nmc_set_axis_enable`）、回零参数（`nmc_set_home_profile` +
  `nmc_home_move`）、总线诊断（状态机 / 错误码）。
- **EtherCAT 端口号固定为 2**：`nmc_get_errcode(card, 2, ref …)`、`nmc_get_total_slaves(card, 2, …)`。
- **CiA402 状态机只有 4（操作使能）能动**：0 未启动 / 1 启动禁止 / 2 准备启动 / 3 启动 /
  4 操作使能 / 5 停止 / 6 错误触发 / 7 错误。
- 回零完成读 `dmc_get_home_result(card, axis, ref state)`，**`state == 1` 才算成功**；
  `LTDMC.dll` 里**根本没有** `dmc_check_home_done`。
- `dmc_get_CardInfList(ref num, uint[] cardTypes, ushort[] cardIds)` —— 第 2 个 `uint[]`、
  第 3 个 `ushort[]`，顺序别弄反。
- 卡型：DMC-E 总线卡 = `0xE000E000`（`dmc_get_CardInfList` 的 `CardTypeList` 第 3 项）。

### IO 寻址：保留「整卡位号」，不擅自改（有意的决定）

- 官方例 8 在**总线卡**上仍然是 `dmc_read_inbit(card, 位号)` / `dmc_write_outbit(card, 位号)`
  按整卡位号逐位访问（位号 0..23），点数从 `nmc_get_total_ionum(card, ref in, ref out)` 读。

## 20) 顺着调用链往下查：自动识别把总线卡登记成「脉冲卡」

上一节做完后继续查「桥接层到底有没有被用上」，结论是通的：

```
Lua Axis.MoveAbs("X轴",10) → Services/HardwareApi.cs → IHardwareBridge
  → LeadshineHardwareBridge → LtdmcCard → LtdmcNative → LTDMC.dll
```
`HardwareSetup.AutoDetect() => UseLeadshine()` → `new LeadshineHardwareBridge()` →
`HardwareBridge.SetBridge(...)`。**雷赛层之外没有任何代码直呼 `dmc_*` / `nmc_*`**
（`grep -rln "dmc_\|nmc_"` 排除 `Services/Hardware/Leadshine/` 后为空），
`LtdmcCard` 只在 `HardwareSetup.cs` 与 `ViewModels/AxisControllerViewModel.cs` 出现。

### 查出来的真 bug：`AxisControllerViewModel.AutoDetect()` 把 `BusType` 写死成「脉冲」

```csharp
Items.Add(new AxisControllerItem { ..., BusType = "脉冲", ... });   // ← 硬编码
```
插 **DMC-E 总线卡** 点「自动识别」，会被登记成**脉冲卡** —— 用户照着错的分支接线。

改法：读 `LtdmcCard.FirstCard`（探测结果）照实登记 `BusType` / `Connection` / `AxisCount` /
`CardType` / `Description`，并把 `info.Summary` 追加进 `DetectMessage`；总线错误码非 0 时额外警示。

`HardwareSetup.UseLeadshine()` 的就绪串也带上了卡信息摘要（这个串同时被 Lua 的
`HardwareStatus()` 读走，所以「脉冲卡还是总线卡、总线通不通」写在里面）。

### 连带挖出的产品不一致：`Catalog.BusTypeNames` 里没有「其它」

`AxisControllerItem.BusType` 的文档取值集是「脉冲 / EtherCAT / CANopen / Modbus / Profinet / 其它」，
`CardVendorRegistry.BusTypeName` 也把 `CardBusType.Other` 映射成「其它」，
但**没有任何厂商条目声明过 `Other`**，而 `Catalog.BusTypeNames` 是从厂商登记表生成的 →
下拉框候选里根本没有「其它」（实测：脉冲 / EtherCAT / CANopen / Modbus/TCP）。
所以「总线卡但没扫到 EtherCAT 从站 → 填其它」这个如实做法**会让 ComboBox 渲染成空白**，
看起来就像「自动识别坏了」。已给雷赛条目补上 `CardBusType.Other`。

**这是冒烟 U 段里那条「自动识别可能写出的值必须都在候选里」断言抓出来的 —— 断言本身发现了 bug。**

### 两个工程教训

1. **警告数 590 → 592，但我改的文件一条警告都没有。** `-v q` 对分析器警告不给文件行号，
   `grep warning | grep 我改的文件` 也是空的，看起来像「不是我加的」。
   真因：新增的 `DescribeBusType(LtdmcCard.CardInfo info)` 触发了 **CS8604**（可空引用实参）。
   定位办法：**只把我改的两个文件还原成旧版重建，警告数回到 590 → 确认是我加的**；
   再 `-v n` 把两边的警告清单归一化后 `diff`，直接看到那一行。
   修法：参数写成 `LtdmcCard.CardInfo? info`（`LtdmcCard.cs` 是 `#nullable disable`，
   但 `AxisControllerViewModel.cs` 是 nullable-enabled，传 `FirstCard` 会告警）。
2. **`DescribeBusType` 从 ViewModel 挪到了 `LtdmcCard`（`public static`）**：
   这是「卡型知识」，属于控制卡层；放这儿才能被冒烟直接断言（原来 `private static` 测不到）。

## 卡族层：底层 dll 清单「照代码实际调用」重扫

### 原来的清单是错的（按目录名猜出来的）

`CardFamilyCatalog.Families[].NativeDlls` 最初是按目录名 + 参考工程 csproj 的部署清单**猜**的。
这轮写了 `ncm_patch/depmap.py`：**先把注释剥掉**，再扫 `DllImport` + 扫「调用了哪个 Native 包装类」，
两者并起来才是真依赖。一比对，**11 个卡族的清单是错的 / 缺的**：

- **`HY7X00`（恒昱）主驱动不是 LTDMC.dll** —— `HY7X00SDK.cs` 全篇调 `PCI400.*`，
  真实驱动是 **`PCI400.dll`**（`Native/PCI7800.cs` 里那个 `class PCI400`）。
  只有 1 个高速比较器配置 `LTDMC.dmc_compare_set_config` 走雷赛库。
- `SoftServo` 除 WMX3 那组托管程序集外，**EtherCAT 主站复位调的是 `MCCE135.*`，
  错误码读取调 `LTDMC.nmc_get_errcode`**（参考实现自己抄过来的，我逐字保留 → 清单必须照实列）。
- `DMC1000S` / `E64IOSeries` / `EC600` / `HYMC608` / `PLTEI400H` / `SLD1230` / `SLD1232` /
  `VirtualMotionCard` 都额外 P/Invoke `LTDMC.dll`（多是高速比较器 / 急停那几个接口）。
- `PCI9014` 还引 `SLD9014PTP.dll`（参考工程未随附）。
- `pci1230.dll` 源码里是小写，落盘改成了 `PCI1230.dll`（Windows 不敏感，清单按落盘名写）。

**教训：不要按目录名猜底层库。** 扫的时候一定要先剥注释 ——
`//return LTDMC.xxx(...)` 这种注释掉的调用满仓都是，不剥会把 LTDMC 摊到几乎每个卡族头上。

### 清单与调用必须双向对得上（已固化成断言）

冒烟 W 段两条硬断言，任何一边漏了都 FAIL：

1. **正向**：移植代码里每个 `DllImport` 的库，都必须出现在某个卡族的 `NativeDlls` 里
   （唯一放行 `winmm.dll` —— 高精度计时工具类用的系统库，不属于任何卡族）。
2. **反向**：`NativeDlls` 里每个原生库都必须真的有调用
   （唯一放行 SoftServo 那 6 个托管程序集 —— 它们是 `Reference`，不是 `DllImport`）。

实测 **17 个原生库**，双向全对得上。X 段会把本机缺的库打成清单
（当前缺 `MCC.dll`、`Dmc2210.dll`、`SLD9014PTP.dll`；缺库只影响初始化，不影响编译）。

### `Resolve` 的「只给品牌 + 总线」分支会挑错卡

`Resolve("研控", "", "EtherCAT")` 原来返回 **YKMCC400S**（它 `BusTypes` 里也有 EtherCAT，
但声明顺序在 `YKMCCE3032` 前面）。同品牌好几张卡都支持 EtherCAT 时，「第一个命中」没有道理。

改成：**先挑「纯总线」的（`BusTypes` 里不含 Pulse）**，也就是专职总线主站；
没有再退到任何支持总线的。于是 研控+EtherCAT → `YKMCCE3032`，研控+脉冲 → `YKMCC400P`。

### Lua 断言：C# 委托注册进 Globals 是 `ClrFunction` 不是 `Function`

`script.Globals["UseCardFamilies"] = (Func<string>)...` 之后 `Globals.Get(...).Type`
是 `DataType.ClrFunction`。断言写成 `DataType.Function` 会**假失败**（调用本身完全正常，
下一行 `script.Call` 就返回了正确中文串）。仓里既有断言用的就是 `ClrFunction`。

### 工具教训：同一文件的两个 Edit 不能并行发

同一条消息里对**同一个文件**发两个 Edit，第二个会把第一个覆盖掉 ——
两条都报 success，但只有一个真的落盘。改完必须 `grep` 复查。

## 卡族层：固件卡型码别名 + 两个品牌归属修正

### 固件卡型码：自动识别写进「卡型号」的是 0xHEX，不是型号名

`AxisControllerViewModel.AutoDetect` 第 73 行对雷赛卡写的是
`CardType = info.CardType == 0 ? "DMC" : $"0x{info.CardType:X}"` —— **固件上报的卡型码**。
原来 26 个卡族里只有 DMC3400A 登记了 `0x3400`/`0x3800`，其余全是型号名关键字。
后果：混装工程里（有非雷赛卡 → 切到卡族层）这张卡匹配不到卡族，会掉到
`Resolve` 的「品牌 + 总线」兜底分支，**被配上一张不相干的同品牌卡**。

码从参考实现 `SystemHardwareData.cs` 里「卡型码 → 卡族」的 switch 抄出来（脚本
`ncm_patch/fw_codes.py` 抽取，落了一份 `fw_codes.json`），**48 个新别名**，含十六进制与十进制两种写法。
覆盖：DMC1000S 0x2711、DMC3400A 0x3C00、DMC_E3032 0x80013032、E64 0xE6416/0xE6432、
EC600 0xEC600、HY7X00 0x7400/0x7600/0x7800/0x7C00、HYMC608 0x608、研控 0x4040/0x8040/0x8076/0xF00/0x7E2、
PLTEI400H 0xD430、SLD1230/1232 0x1230/0x1232、虚拟卡 0x1B198（111000）、仿真卡 0x877F8（555000）。

**两个坑**：
1. 别名匹配是**子串**匹配，短数字别名会串味。写脚本时加了个安全阀：十进制串若是别的卡族
   键/别名的子串就丢掉（`9014`/`9016` 因此被跳过 —— 它们本来就已经是别名了）。
   另外「420」「421」（MCN42）太危险，只登记十六进制形式。
2. 参考实现把 **MCC400S 与 MCC800S 都上报成 0x8076**（它自己的复制粘贴 bug）。
   按 `0x4040=400P` / `0x8040=800P` 的规律，`0x80xx` 属 800 系列 → 0x8076 归 **MCC800S**，
   400S 不登记该码（Note 里写明了）。

新增反向守卫断言：加了这些码之后，`DMC1000S` / `DMC3400` / `DMC-E5000` / `MCC800S` /
`MCC800P` / `HY7C00` / `E6432` 的型号名匹配**不能**被抢走（最长命中优先）。

### MCC141C 与 EC600 原来被我错标成「未分类」

参考实现的分组规则（`SelectControllerDialog.xaml.cs` 的 `BuildCardTree`）逐条是：
含 DMC+E→雷赛总线；DMC 不含 E→雷赛脉冲；**前缀 PCI/E/F→升立德**；前缀 HY→恒昱；
**前缀 MCC 含 E→研控总线；MCC 不含 E→研控脉冲**；含 虚拟/仿真→模拟卡。

按规则重算：
- **`MCC141C` → 研控（脉冲）**：前缀 MCC 且不含 E 命中；它的包装类命名空间 `csMCC1C00`
  也属研控的 `csMCC*` 命名族。保留说明：它**没出现在参考实现的两个卡型枚举里**，
  所以参考实现的卡树里本来也看不到它 —— 归属是推断的，Note 里写清楚了。
- **`EC600` → 升立德**：前缀 E 命中；且它在 `SystemSupportMotionCardEnum` 里紧挨着
  升立德的 E64xx 区块（`… MCCE332, EC600, E6432, E6416 …`），参考实现的卡树就是这么归的。
- `PLTEI400H`（前缀 PLT）与 `SoftServo`（前缀 S）**确实**两个规则都覆盖不到 → 保留「未分类」。
  所以未分类从 4 个降到 **2 个**。

连带好处：`Resolve("升立德", "", "EtherCAT")` 现在能匹配到 EC600（此前升立德全是脉冲卡，匹配不到）。
`CardVendorRegistry` 的 升立德/研控/未分类 三条也同步挪了 Families/CardTypes/DllNames，
顺手把恒昱那条写错的「HY7X00 走 LTDMC.dll」改成 PCI400.dll。

### 反面教材：冒烟测试与 `--no-incremental` 构建**绝对不能并行**

两个都写 `D:/wqz/code/NoCodeMotion//obj//`。并行跑的结果是互相删对方的中间产物，
报出 **92 个错误 / 295 个警告**，全是假错：

```
error CS0103: 当前上下文中不存在名称"InitializeComponent" / "RowsBox" / "NameBox" ...
error CS5001: 程序不包含适合于入口点的静态 "Main" 方法
error CS2001: 未能找到源文件"...\obj\Debug\net10.0-windows\MainWindow.g.cs"
```

（XAML 生成的 `*.g.cs` 被另一边删掉了。）
**而且这个状态不会自愈** —— 之后再单独跑，增量构建认为 obj 是最新的、不重新生成
`*.g.cs`，于是继续报同样的错。修法：`rm -rf obj bin` 再全量 build（本次实测 37 秒，回到 590/0）。

**判断依据**：错误里出现 `CS0103 InitializeComponent` / `CS5001 没有 Main` / `CS2001 缺 *.g.cs`
→ 一律先怀疑 obj 被污染，不要去改代码。

### 两个坑（都是验证脚本自己的，不是产品的）

1. **取样方式错了会得出完全相反的结论。** v1 用「标签之后一路读到下一个有名字的 TextControl」
   取候选，结果只报出 1 项（「雷赛」），8 条断言全 FAIL —— 看起来像「下拉坏了」。
   真因：**ComboBox 内部的可编辑文本框本身就是一个有名字的 TextControl**（显示当前选中值，
   正好是「雷赛」），所以读到第一项就 break 了。改成直接取 ComboBox 的 `ListItemControl`
   子孙后 13 项全出。**结论：UIA 报「只有一项」时先怀疑取样，别先怀疑产品。**
2. **不要在脚本里断言桌面前提。** 我照着旧笔记断言「`GetForegroundWindow()` 必须为 NULL」，
   结果它返回非 0 → 前提断言直接 FAIL。实际这机器**现在有交互式桌面**（光标在 (1203,453)）。
   旧结论已经过期，改成「只打印不断言」，并已更正 MEMORY.md 里那条。

顺带：managed python（3.13.12）同时有 `PIL` 和 `uiautomation`，系统 Python 3.12 **没有**
uiautomation —— 跑 UI 脚本要显式指定 managed 那个。
