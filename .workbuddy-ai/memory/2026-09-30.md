## 追加五：现场截图「Jog 失败（卡返回 8194）」——已排除模拟卡，指向研控 MCN420

## 追加七：8194 的真因 = `Channel = 2`（非法通道）；前后两轮都在追错方向

**真因（与上一轮的「缓冲被占」假设不同）**：`MCN420SeriesSDK` 里给请求结构体的
**`Channel` 字段硬编码写了 `2`，而合法值只有 `0` / `1`**。

证据链（都在 `Native/MCN420.cs`）：
- `Jog_Req_Param.Channel` / `Single_Req_Param.Channel` / `SetInputCounter_Req.Channel` /
  `SetOutputDelayFlip_Req.Channel` **每一条原生 struct 注释都写 `// 0 or 1`**。
- `YK_vmove` 文档：「Channel：**通道0 or 1**；注意：点位运动下**通道默认写0即可**」。

  `= 2` 极可能就是把它误当成了 Channel 的取值。
- 卡无法解析通道 2 → `YK_vmove` 直接回 **8194「普通缓冲满」**（卡是按通道索引缓冲的）。
  这也解释了**为什么点「停止」救不回来**：根本不是「被占」，是通道号本身非法。

**改了 4 处**（`MCN420SeriesSDK.cs`）：`Channel = 2` → `Channel = 0`
① OpenCard 预置 `AxisVMoveParaDic`(Jog)；② 同处预置 `AxisPMoveParaDic`(点位)；
③ **`DmcSetCardAxisProfileUnit` 重建的 Jog_Req_Param（Jog 实际走这条 —— 这才是现场的直接来源）**；
④ `DmcSetCardIOCountMode` 的 `SetInputCounter_Req`。
保留 1 处注释里的 `// Channel = 2`（`YK_set_output_delay_flip` 被注释掉的代码，无害）。

**★ 教训：错误码的中文名会骗人。**「8194 = 普通缓冲满出错」听起来就是「缓冲里有东西」，
于是上一轮绕去搞「先停再 Jog + 读缓冲占用」，方向偏了。**参数合法性要先查**：一个字段
值域写错，卡往往只回一个语义相近的码。下次遇到某个码查不出原因，

## 追加九：「轴移动很慢、速度填多大都没用」——加减速字段语义错（真因）

用户反馈：Jog 能走了（Channel 修好了），但**轴走得非常慢**，手动速度填 20000 也没用。

### 排查路径（一步步逼近）

1. 先算出 `BuildMotionParam` 的 `tacc = v / accel = 20000 / 50 = 400 秒` ——
   疑似「400 秒加速斜坡」。
2. 再看卡层 `DmcSetCardAxisProfileUnit`：`InterpoAcc = (v/1000)/(tacc*1000)`。
   **代数一算发现它恒等于 `accel/1e6`** —— 也就是「accel 由 unit/s² 换成 unit/ms²」的正确值。
   **所以「公式写错」是假象，改公式没用。**
3. 查 `Native/MCN420.cs` 里 `YK_vmove` / `YK_pmove` 的原生文档：`InterpoAcc` 就是
   **加速度 unit/ms²**（`ParaType=1 有加速度参数`），`InterpoSpeed` 是 unit/ms。
4. 查 `Interfaces/IAxis.cs` 文档：**`TaccVel 加速时间 单位 s`** ——
   桥接层本来就该给一个**时间**，旧代码给的是「除以速度后的伪时间」。
5. 结论：**真正的 bug 是语义层** —— `AxisItem.Accel` 是「加速度值」，
   但被 `v/accel` 转成了一个「伪加速时间」，再被卡层当「速度差/时间」当成真时间用。
   `v=20000` 时斜坡 400 秒 → 轴全程在斜坡底部爬 → 「速度填多大都一样慢」。

### 修法（用户拍板：Accel 按「加速时间(秒)」理解）

- `BuildMotionParam`：`tacc = axis.Accel > 0 ? axis.Accel : 0.2`（不再 `/accel`）；
  `tdec = axis.Decel > 0 ? axis.Decel : tacc`。
- `BuildHomeParam`：`TaccTime/TdecTime` 同口径（不再 `high/Accel`）。
- `AxisItem._accel/_decel` 默认 `50 → 0.2`（秒）。
- `ProjectData.MigrateAxisDefaults`：旧默认 `50 → 0.2`（只动等于旧值的轴，用户设的值保留）。
- 雷赛 `LtdmcCard.ApplyAxisProfile/SetSpeed/Home` 三层同步改（`dmc_set_profile_unit` 的 tacc 本就是秒）。
- Jog 日志写明 `unit/s + 脉冲当量 + 加减速秒数`；`Accel>=5s` 时状态栏主动告警。

### 单位换算的结论（用户选「引入脉冲当量换算」）

- 卡族指令是 **unit 版**，卡内用 `YK_set_command_ratio`(pulse/unit) 自己换算
  → **真实卡下发 unit/s 原值，桥接层不能乘当量**；
- **模拟卡没有这层** → `BuildSimParam` 自乘当量换 pps（并给 1000pps 下限）；
- 两者都已结构性正确，本次补的是**日志可见性**（让现场能核对换算）。

### 验证

- 守卫：**95 → 109 PASS / 0 FAIL**（新增 G11.9/G11.10 迁移扩展 + 整段 G12 共 12 条）。
- 冒烟：**64 → 76 PASS / 0 FAIL**（Z11–Z15 默认值/迁移 + 整段 AA：**反射真实调用
  `BuildMotionParam`**，断言 tacc 不被速度放大、且**与速度无关**——旧公式会给 400/2，新逻辑恒为原值）。
- 构建 **0 错误**（DLL 15:33:25）。

### 教训

- **「改公式」之前先做代数化简**：`(v/1000)/((v/a)*1000) ≡ a/1e6`，一眼能看穿
  「公式看着错、实际是恒等式」。错的是**输入语义**，不是算式。
- **一个字段同时存在「值」和「时间」两种语义的 API，必有 `ParaType` 之类的开关**：
  本项目卡层 `InterpoAcc`(值) 与 `InterpoAccTime`(ms) 并存，`ParaType` 1/2 选模式。
  写这类 API 前先确认**当前工作在哪种模式**，别把「时间」塞进「值」槽。
- **改字段语义 = 改契约**：必须同时改 ① 计算处 ② 默认值 ③ 迁移 ④ 全部 parallel 实现（雷赛层）
  ⑤ 加自诊断（旧大数残留会静默变慢）。漏任一条都会留下「改了一半」的坑。
- **测试期望写错也是真信号**：AA1/AA2 最初断言 `tacc==0.2`（我以为会兜底），
  实际是 `50`（用户填的值原样传）—— 这个 FAIL 帮我看清「残留 50 会变 50 秒」，
  直接催生了迁移 + 自诊断两项改进。**FAIL 先想「谁对」，别急着改代码去迎合测试。**
